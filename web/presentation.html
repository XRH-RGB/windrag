01 / 项目背景

数据越来越多，
查看、分析和处理需要连起来。

风机数量增加后，人工翻看数据、核对告警和查找资料会花费更多时间。我们把这些任务放到一个系统里，让一次问题处理能够留下完整记录。

01

资料分散

运行数据、风机档案与运维知识分开保存，查找和核对不方便。

02

分析重复

数据需要反复清洗和统计，缺失、重复与异常值影响判断。

03

处理缺少衔接

发现告警后，需要明确谁处理、处理了什么，以及结果在哪里。

建设目标：统一设备与数据入口，形成“数据处理—分析预测—异常告警—运维归档”的闭环，并用知识问答辅助资料查询。

02 / 项目架构

一个平台，两条协作链路。

运行数据支撑分析与预警；知识资料支撑问答与来源追溯。身份和权限贯穿每次操作。

交互层驾驶舱 · 风场与风机 · 数据中心 · 预测与预警 · 运维报表 · 知识问答
服务层登录与会话 → 权限校验 → 数据处理 / 统计预测 / 告警工作流 / RAG 分流
算法层描述统计 · 时间序列持续性基线 · 阈值异常检测 · FAQ 匹配 · BM25 · 可选 BERT、向量和生成模型
存储层SQLite：账号与角色、风场风机、原始批次与观测、预测结果、告警、巡检维修、知识版本、操作日志
业务边界

按身份和风场授权

管理员负责维护与配置；运维人员分析并处理问题；普通用户查看授权范围内的数据与结果。

交付方式

本地启动，浏览器使用

沿用 Python、原生 Web 与 SQLite，一次启动同时提供页面和接口。示例数据固定种子生成。

数据闭环

导入、处理、分析

读取 CSV 并预览，保留原始批次，查看清洗前后差异；统计和图表使用同一数据源。

业务闭环

发现、处理、归档

检测异常并生成告警，记录处理人和结果，将巡检与维修纳入报告。

知识闭环

检索、引用、反馈

问候和 FAQ 快速直出，其他问题检索有效知识，返回证据并保存问答记录。

现场验证顺序管理员登录 → 导入 Demo CSV → 清洗 → 分析 → 预测 → 异常检测 → 处理告警 → 维修记录 → 报告与日志 → 运维 / 普通用户权限验证

演示采用课程数据和本地基线预测；设备状态来自最近历史观测。BERT、向量服务和生成模型按配置接入，状态以系统实际运行结果为准。
